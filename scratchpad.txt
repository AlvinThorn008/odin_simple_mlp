Consider the case kernel_2x16:
If N is simply set to 2 in that inner loop then we'll have 4 independent fma operations in flight. In order
to approach 100% utilization, the outer loop k in [l, r) should be unrolled in steps of (12 / 4 = )3. 

We can do this for cases N=1 to 3, beyond which our model predicts ~80% and ~100% utilization at N=4 and N=5 when using
the more generic specialized(inner loop N set to nr_rem)

Cache blocking implementation

## Rough overview
- Divide C into 6a x 6b sub matrices, denote each one as a C_unit
- To compute a C_unit, we need the sub matrices of A and B with sizes, 6a x P and P x 16b
  where P is the common dimension of matrices A and B. Call these sub matrices A_unit and B_unit
- Instead of computing C_unit completely, it is done partially with 6a x Q sub matrices of A_unit and Q x 16b sub matrices
  of B_unit

I think this version is clearer as it takes into account our kernel size. Computing a C_unit is only requires the fixed kernel(which is the fastest one).

Factorizing in the cache sizes:

P x 16b floats < L3 cache | s3 = 16b
6a x P floats  ~ L2 cache | s2 = 6a
Q x 16b floats ~ L1 cache | s1 = Q

I do want the sizes we pick to be constant but we can't do that right now because P varies with the input. However, 

If I want my all steps to be constant, I need to fix P to say a reasonable maximum value. For smaller P, it's fine especially if I also limit P to a minimum value so my constants let the sub divisions fit their associated cache with a sensible variance. (I could let the non-blocked version handle smaller matrices)
For larger P though, fixed step sizes, the sub divisions could easily exceed their cache size. I guess this is technically fine as with dynamic sizes, for large P, we would end up with s3=16,s2=6
